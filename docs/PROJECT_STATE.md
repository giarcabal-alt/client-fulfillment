Known gotchas (carried forward from the 3PL project — likely to recur here too, since it's the same Supabase/Vercel stack):
- **General pattern to watch for:** this app deliberately uses separate accounts from the 3PL project (Supabase confirmed, GitHub turned out to be separate too). Any CLI tool that caches a single global login (Supabase CLI, git/GitHub credentials, potentially others later) can silently apply the wrong account's credentials to this project instead of prompting for the right one. When something fails with a permissions/403 error that doesn't make sense, check *which account* the tool thinks it's using before assuming the problem is something else.
- This app's Supabase project is on a **different account** than the 3PL project. Don't run global `supabase login`/`logout` to switch between them — instead `export SUPABASE_ACCESS_TOKEN=<token>` (from this account's Access Tokens page) in this project's terminal session only. Forgetting this and running `supabase login` globally will silently point this folder's CLI commands at the wrong account until you switch back.
- This app's GitHub repo is under a **different GitHub account** (`giarcabal-alt`) than the 3PL project (`dani-mgs`). A cached git credential (Keychain or `gh` CLI) for the old account can cause pushes to fail with a 403 "Permission denied" even though the repo URL itself is correct. Fix: `git remote set-url origin https://<correct-username>@github.com/...` to force a fresh credential prompt, or clear the cached entry in Keychain Access / `gh auth login` as the correct account.
- `supabase link` fails on this machine with "does not have the necessary privileges to access this endpoint" — a known, currently-unresolved Supabase platform/CLI bug unrelated to actual account permissions. Workaround in use: `supabase db push --db-url '<pooler-connection-string>'` (Docker Desktop must be running; use the **pooler** connection string, not the direct `db.xxxxx.supabase.co` one — the direct one resolves to IPv6 and fails with `ECONNREFUSED` on networks without proper IPv6 routing).
- **Writing an RLS policy is not enough — Postgres checks table-level `GRANT`s before RLS is ever evaluated.** The initial schema migration created policies but never granted `authenticated` basic SELECT/INSERT/UPDATE/DELETE on the tables, so every write failed with `permission denied for table X` until a follow-up grants migration fixed it. Any new table needs both: RLS policies AND an explicit grant (or rely on the `ALTER DEFAULT PRIVILEGES` clause already in place, which should auto-cover genuinely new tables going forward).
- Supabase's dashboard **Triggers page filters by schema and can hide triggers on `auth.users`** under the wrong tab — a trigger existing and working correctly can look "missing" in the UI. Don't trust that page alone; confirm directly with `select * from pg_trigger where tgname = '...'` in the SQL Editor if a trigger's existence is ever in doubt.
- **Claude Code sessions don't have visibility into `supabase db push` commands you run manually outside its own tool calls.** A fresh session may flag caution about migrations "needing to be applied" even when they're already confirmed live — check this file's §4 (Current State) for what's actually confirmed before re-verifying from scratch, and keep §4 updated after every manual push so this doesn't compound.
- `supabase db reset` fails with a socket error if Docker Desktop isn't fully started yet — wait for the whale icon to settle.
- Migration files sometimes get created and applied but NOT committed to git — run `git status` after any Supabase CLI work and confirm the new `.sql` file is committed before moving on.
- `supabase login` sessions can expire/loop on a Keychain prompt — if a CLI command throws an auth error, just re-run `supabase login`.
- **Native browser/OS scrollbars are not a reliable way to signal "more content off-screen" and can render invisibly even when correctly styled.** After fixing the board's `min-w-0` clipping bug (gotcha above), a follow-up task asked to make the horizontal scrollbar on the board's column row persistently visible (not just on hover/active-scroll) via `::-webkit-scrollbar`/`scrollbar-color`/`scrollbar-width: thin` CSS. That CSS computed correctly (confirmed via `getComputedStyle`) but rendered zero pixels and reserved zero layout space in the Playwright MCP browser session used to verify it — `scrollbar-width: thin` and `::-webkit-scrollbar` alike, even with the "thin" keyword removed. This is a known class of problem: native scrollbar visibility depends on the OS's own "show scrollbars" setting (macOS in particular can force auto-hide-until-scroll regardless of page CSS) and on the specific browser/engine build's scrollbar theming assets, neither of which a page's CSS reliably controls end-to-end. **Fix used instead: don't fight native scrollbar theming — render your own indicator.** `board-client.tsx`'s `useHorizontalScrollThumb` hook tracks `scrollWidth`/`clientWidth`/`scrollLeft` (via a scroll listener + `ResizeObserver`) and drives a small absolutely-proportioned `<div>` track/thumb rendered below the row, hard-hidden by CSS (`scrollbar-width: none` + `::-webkit-scrollbar { display: none }`) from ever showing the native one underneath. This is guaranteed visible on load, in any browser, regardless of OS scrollbar prefs — and was the only approach that actually verified in a screenshot. **If a future task wants a visible scroll affordance anywhere else in this app, replicate this pattern (synthetic indicator + hidden native scrollbar) rather than trying `::-webkit-scrollbar`/`scrollbar-color` alone again** — budget time to discover this the same way if you skip straight to native-scrollbar CSS.
- **A `flex-1` element nested inside another flex container needs an explicit `min-w-0` (or `min-h-0` for columns) whenever a descendant relies on `overflow-x-auto`/`overflow-y-auto` to scroll instead of clip.** By default a flex item's `min-width`/`min-height` is `auto`, which means it won't shrink below its content's intrinsic size — so if that content is wider than the available space, the flex item itself grows to fit it instead of respecting the parent's bound, and the growth cascades up the ancestor chain instead of triggering the intended scrollbar on the nearer, correctly-configured `overflow-x-auto` container. This is exactly what took three attempts on the talent-acquisition board: `board-client.tsx`'s column row (`overflow-x-auto`) was correctly configured from the start, but `src/app/(shell)/layout.tsx`'s `<main className="flex-1 ...">` had no `min-w-0`, so at any viewport width where the columns' combined intrinsic width exceeded the available space, `main` (and the page around it) grew instead of letting the column row scroll internally — producing overflow/clipping that looked like "the scroll container is broken" when the actual bug was one ancestor level up. Fix applied: `min-w-0` added to that `main` element. **When a scrollable region clips instead of scrolling, check every `flex`/`flex-1` ancestor between it and the viewport for a missing `min-w-0`/`min-h-0` before touching the scrolling element's own CSS again.** This same pattern keeps showing up on ordinary `flex justify-between` header rows too (candidate name + status badge, board title + "Manage roles" link, History rows) — any two-sided flex row with variable-length text on one side needs `min-w-0` (or `flex-1 min-w-0`) on the growable side, or `flex-wrap`, or both, or narrow viewports clip it. Check for this by default on any new one, don't wait for it to be reported.
- **This UI kit (`@base-ui/react`, via shadcn's `sheet.tsx`/`dialog.tsx`) has no `asChild` prop** — that's a Radix convention this kit doesn't share. To render a custom trigger element (e.g. a styled `Button` as a `SheetTrigger`), pass it via the `render` prop instead: `<SheetTrigger render={<Button>…</Button>} />`, not `<SheetTrigger asChild><Button>…</Button></SheetTrigger>`. Passing `asChild` is a TypeScript error (`Property 'asChild' does not exist`), so this fails at typecheck, not silently at runtime — but worth knowing up front rather than rediscovering.
- **Supabase's default email sender has a very low rate limit meant for testing only.** It's fine for the occasional manual invite during development (and is the backstop confirmed working during the admin invite feature, step 2 — see §4), but real invite usage will hit `over_email_send_rate_limit` quickly. This needs a custom SMTP provider (e.g. Resend) connected in the Supabase dashboard before invites are used for real — not a code fix, nothing in this repo's Server Actions can raise Supabase's own project-level limit. Flagged during step 2, deferred until now as a reminder to actually do it before relying on invites at any real volume.
- **Base UI's `Sheet`/`Dialog` don't auto-close when a plain `<Link>` inside them navigates** — there's no implicit `SheetClose` wrapping every nav item the way some kits behave. If a Sheet holds navigation links (as `mobile-nav.tsx`'s slide-out menu does), it must be a controlled component (`<Sheet open={open} onOpenChange={setOpen}>`) that explicitly closes itself on route change, or the menu stays open over the new page after a tap. Do the state reset **during render**, not inside a `useEffect` — `useEffect(() => setOpen(false), [pathname])` triggers this repo's `react-hooks/set-state-in-effect` ESLint rule (an extra unnecessary render pass) and is flagged as an error, not a warning. The working pattern (see `mobile-nav.tsx`): track the last-seen `pathname` in state, and if the current `pathname` differs, call both setters directly in the render body (React's documented "adjusting state when a prop changes" pattern) — no effect needed.
- **Supabase's default email sender changed on June 3, 2026: any free-tier project created after that date cannot edit its Auth email templates at all** — the dashboard's Email Templates editor is locked to Supabase's own defaults (view-only) unless a custom SMTP provider is connected. Projects created before that date were grandfathered with template-editing still enabled; this project wasn't, since it was created after the cutoff. This is what actually blocked the hash-fragment-vs-`token_hash` template fix (below) from taking effect the first time it was tried — editing the template in the dashboard appeared to save, but had no effect on the emails actually sent, until Resend was connected as custom SMTP. **If a future Supabase-auth project's email templates seem impossible to change, or changes to them don't seem to take effect, check whether SMTP is connected before assuming the edit itself is wrong.**
- **The default invite/recovery email link uses a hash-fragment token (`#access_token=...`), which never reaches the server** — this is why the original invite flow silently landed on `/login` instead of `/set-password`, with no error anywhere to point at the real cause. The fix: customize the Invite/Reset Password email templates (once template editing is actually available — see the SMTP gotcha above) to use the `token_hash` query-param format pointing at `/auth/confirm`, which this app's route handler (`verifyOtp()`) can actually read server-side. **Worth checking for on any future project using Supabase auth links** — the failure mode looks exactly like a routing bug in application code, not a template/email-delivery misconfiguration, until you know this pattern exists.
- **A domain existing in Resend's dashboard does NOT mean it's verified** — check the actual DNS record verification status per-domain, not just presence in the domain list. "Not started" means the DNS records Resend generated were never actually added at the domain registrar; a domain in that state can't send mail through Resend regardless of how long it's been listed there.
- **`onboarding@resend.dev` is Resend's built-in test sender** — works immediately with zero domain verification, useful for unblocking real end-to-end testing of an email flow before a real domain's DNS records are set up and verified. Not meant for production sends to real users — see §7's open item on switching to a verified UpScaleSupport domain before this app's invite flow is used on a real hire.

Project-specific watch-item (not yet encountered here, but worth checking every session given the design history — see §10):
- Confirm the AI draft-generation call still only happens from a server action, never a client-side fetch. This app's design went through a version that called the Anthropic API directly from the browser before it was corrected — if any regression reintroduces that pattern, the API key would be exposed to anyone who opens dev tools.

## 10. DO NOT TOUCH / FRAGILE AREAS

- **The Anthropic API call must stay server-side.** An earlier prototype iteration called the API directly from the browser; this was corrected specifically because it would expose `ANTHROPIC_API_KEY` to anyone who opened dev tools. Now built for real as `generateSuggestedMessage()` in `src/lib/talent-acquisition/draft-actions.ts` — the only file in this codebase that calls `api.anthropic.com`, confirmed by direct inspection when it was built, not just assumed. `draft-generator.tsx` (the client component) only ever calls that `"use server"` action; it has no import of `config.anthropic` and issues no `fetch` of its own. Any future change here needs the same auth + org check described in `BUILD_BRIEF.md` §5 before it touches the API. Also worth knowing: **Anthropic's API rejects an unscoped (org-level) API key with a 400 unless every request also carries an `anthropic-workspace-id` header** — this app's own `ANTHROPIC_API_KEY` hit exactly this live, confirmed via a direct `curl`, not a code bug (see §6/§7). Optional support for the header exists (`ANTHROPIC_WORKSPACE_ID` in `config.ts`/`.env.example`) — set it only if the configured key is unscoped; a workspace-scoped key needs no such header at all.
- **`getUser()`, never `getSession()`**, anywhere auth state is checked server-side, per `SECURITY.md` — `getSession()` trusts a locally-stored JWT without revalidating it.
- **Every table gets `org_id` and RLS enabled on creation**, even though there's only one org today — this is what makes a future second org (or the eventual client/lead-gen app) a data change instead of a security rewrite. Don't add a table that skips this.
- **The Talent Pool stage (`talent_pool`) must not get a cadence config with `touches` or `recurDays`.** No reminder pressure on parked candidates is a deliberate design choice, not an oversight — adding one back would undo the reason the pool exists.
- **`roles.job_description` is the single source of truth for a requisition's JD**, not a per-candidate field — don't reintroduce a candidate-level job description column; it was deliberately removed to avoid duplicating the same text across every candidate on one role.
- **Any Server Action with a side effect (the AI draft generator, any future third-party API call) needs its own authorization check beyond RLS** — RLS protects direct DB reads/writes, but an action calling an external API needs an explicit org/ownership check per `SECURITY.md`.
- **Any Server Action accepting a foreign-key ID into another org-scoped table must re-verify visibility itself, not trust the FK constraint.** RLS on the referenced table only governs direct access to that table — a FK constraint just checks the row exists, not whether the caller is allowed to see it. `candidates-actions.ts`'s `assertRoleIsVisible` pattern (re-running the caller's own scoped SELECT on `role_id` before accepting it) is the template to copy for any future action taking an org-scoped foreign key.
- **`statusFor` must keep checking `talent_pool` before anything else, unconditionally.** It's not enough that `STAGE_CONFIG.talent_pool` has no touches/recurDays — a future change to that config (or a bug in `nextActionFor`) must not be able to make a parked candidate show as overdue. The explicit `if (candidate.stage === 'talent_pool') return 'parked'` at the top of `statusFor` is the actual guarantee, not an emergent property of the config.
- **Any future admin-only Server Action must call `requireAdmin()`/`getUserRole()` (`src/lib/auth/get-user-role.ts`) and check the result explicitly inside the action itself, not only hide the admin UI that links to it.** RLS's existing policies enforce org membership, not role — a signed-in member can already read/write everything a fellow org member can per current RLS, so nothing in the database itself stops a non-admin from invoking an "admin" action directly (e.g. via browser dev tools calling the action) unless the action's own code checks role. - **Any `storage.objects` RLS policy that derives org/ownership from a path segment must regex-guard the segment with `~` before casting it to `uuid` — never cast straight from `storage.foldername(name)` output.** A bare `(storage.foldername(name))[1]::uuid = public.current_org_id()` throws a hard Postgres error (`invalid input syntax for type uuid`) the instant *any* object in the bucket has a non-UUID-shaped first path segment — a stray upload from an unrelated bug, a manually-created test object, anything. Because RLS policies for one command combine into a single evaluated expression, that one throw can abort the *entire* query, silently blocking every other policy on the table too, not just access to the offending row — this reads as "the whole feature is broken" with no obvious cause, not as "one bad row." - **A `Select` trigger's default width is `w-fit` (sized to its selected label's text), which only "just works" inside a wide enough container — narrowing that container (e.g. moving a form from a full-width card into a narrower persistent side column) can silently make longer-content triggers overflow their grid cell with no visual error, just content bleeding past the cell boundary.** Every `Select` in `candidate-detail-form.tsx` needed an explicit `className="w-full"` added to its `SelectTrigger` when the candidate detail page's restructure (see §4) moved this form from a ~768px-wide single card into a roughly-a-third-width left column — the Role and Communication triggers, whose selected-value text is longer than most, were confirmed overflowing by 25–58px via `getBoundingClientRect()` before the fix. Any future move of an existing `Select`-heavy form into a narrower container needs the same check: measure trigger vs. container rects live, don't assume a `Select` that looked fine in its old container will still fit in a new, narrower one.
- **When a migration's new columns need to be added to a `SELECT` that an already-shipped, high-traffic page depends on, sequence the work so that `SELECT` change happens only after the migration is confirmed live — never before.** PostgREST (and therefore every `supabase.from(...).select(...)` call in this codebase) errors the *entire* query if even one selected column doesn't exist yet, not just the missing field — so wiring new columns into `candidates/[id]/page.tsx`'s main select before `20260922160000_add_talent_bench_fields.sql` was applied would have made every candidate's detail page 404 (via the existing `if (!candidateRow) notFound()` fallback) until someone ran the migration. The Talent Bench task handled this by building every other piece first (Server Actions, the new route's own queries, `StageChip`) while asking the user to run `supabase db push` in parallel, confirming the columns live via a direct REST check, and only then touching the shared candidate detail `SELECT`. **Apply this sequencing to any future migration that adds columns an existing page's main query needs** — the risk is specific to columns joining an *already-relied-upon* select, not to genuinely new, not-yet-linked routes (a new route's own broken query before its migration lands is low-risk, since nothing links to it yet).
- **A client component whose "initial" prop-derived state comes from a Server Component's `searchParams` does NOT get a fresh mount just because the URL's query string changed — same route, different query, is still "the same component instance" to React unless something forces a remount (a changed `key`, or navigating to a genuinely different route).** `talent-bench-client.tsx`'s `useState(initialStatus)` only ever consumed its initial value once; clicking the sidebar's "Rejected" then "Talent Bench" (both resolve to `/talent-acquisition/talent-bench`, differing only by `?status=`) silently kept whatever `status` was already in local state after the first landing, not the new `initialStatus` the second navigation's `searchParams` produced — this shipped without being caught until it was actually clicked through twice in Playwright, not just checked by reading `initialStatus` was wired in. **Fix and reusable pattern**: track the last-seen prop value in its own state, and if the current render's incoming prop differs, call both setters directly in the render body (React's documented "adjusting state when a prop changes" pattern) — the exact same shape `mobile-nav.tsx` already uses to close its `Sheet` on `pathname` change, now with a second real use site. Any future feature that seeds client state from `searchParams` on a route two different nav items can both point at (with only the query differing) needs this same treatment — don't assume `useState(propFromSearchParams)` is enough just because it works correctly on first load.
- **This UI kit's `Select` value span (`components/ui/select.tsx`'s `SelectValue`, `@base-ui/react` under it) sets `display:flex` on itself, which silently disables its own `line-clamp-1` ellipsis truncation — a long value just clips mid-character with no "…" instead.** `line-clamp`/`-webkit-line-clamp` only renders its ellipsis on a block or `-webkit-box` display container; `flex` overrides that, so the clamp CSS is present in the computed styles but visually inert. This was invisible in every `Select` before the density pass because the app's cards were wide enough that values rarely needed to truncate at all — it only became visible once `PropertyRow`'s narrower value column made "AI Solutions Engineer" actually hit the edge. **Fix, and the pattern for any future narrow `Select` usage**: force block-level truncation on the inner value span specifically (`[&_[data-slot=select-value]]:block [&_[data-slot=select-value]]:overflow-hidden [&_[data-slot=select-value]]:text-ellipsis [&_[data-slot=select-value]]:whitespace-nowrap`, see `propertySelectTriggerClass` in `property-row.tsx`) — don't assume the existing `line-clamp-1` on `SelectTrigger`'s base classes is sufficient just because it "worked" in every wider context so far.
- **DESIGN_SYSTEM.md's Density §5 properties-list pattern (small label, plain value, hover/focus-only editing chrome) trades away a visible-at-rest control boundary for a tighter, less-AI-generated-looking record view — and that tradeoff has a real, measured cost on touch devices, not just a theoretical one.** A `PropertyRow`'s `Select`/`Input` control (via `propertyControlClass`/`propertySelectTriggerClass`) renders at a 32px-tall hit target on a 375px mobile viewport (confirmed via `getBoundingClientRect()`), under the 44px touch-target recommendation (WCAG 2.5.5, AAA-level — not required at this app's AA target, so this is not a compliance failure, just a real usability tradeoff). Flagged in the `/impeccable audit` run on the candidate detail page (19/20, the one point lost here) rather than silently patched mid-task, since growing the control's padding to hit 44px would directly undercut the density this task was asked to achieve — that's a real tension to resolve deliberately (e.g. extra vertical padding on the hit area specifically below the `sm:` breakpoint, keeping the visual row compact on desktop), not a reflexive fix. Any future page adopting `PropertyRow` on primarily-mobile content should make this call explicitly rather than assuming the desktop-tuned default is fine everywhere.
- **Before "fixing" a visually-described bug report (e.g. "the sidebar background stops partway down"), reproduce it live first — a plausible-sounding CSS explanation is not the same as confirmed broken behavior, and a confident-sounding fix for a bug that doesn't reproduce is itself a regression risk for no benefit.** The candidate-detail density task also asked to check the sidebar's full-height fill; direct measurement (`aside.offsetHeight` vs `document.documentElement.scrollHeight`, both a short page and one forced to scroll via a short viewport, both confirmed visually via full-page screenshots) showed it already matches exactly in every case tested — the reported symptom did not reproduce against this codebase's current `layout.tsx` (`min-h-full flex-1` on the shell div, sidebar and main as `flex` row siblings under default `align-items: stretch`). Documented as checked-and-working, no code touched. If a future report of the same symptom does reproduce, the first thing to check is whether some *other* page's content sits in its own `overflow-y-auto` sub-scroll (as `board`/`talent-bench` already do) in a way that changes `main`'s own natural height relative to `aside` — not yet observed, but the shape of container most likely to eventually break this stretch-based approach.
