Known gotchas (carried forward from the 3PL project — likely to recur here too, since it's the same Supabase/Vercel stack):
- **General pattern to watch for:** this app deliberately uses separate accounts from the 3PL project (Supabase confirmed, GitHub turned out to be separate too). Any CLI tool that caches a single global login (Supabase CLI, git/GitHub credentials, potentially others later) can silently apply the wrong account's credentials to this project instead of prompting for the right one. When something fails with a permissions/403 error that doesn't make sense, check *which account* the tool thinks it's using before assuming the problem is something else.
- This app's Supabase project is on a **different account** than the 3PL project. Don't run global `supabase login`/`logout` to switch between them — instead `export SUPABASE_ACCESS_TOKEN=<token>` (from this account's Access Tokens page) in this project's terminal session only. Forgetting this and running `supabase login` globally will silently point this folder's CLI commands at the wrong account until you switch back.
- This app's GitHub repo is under a **different GitHub account** (`giarcabal-alt`) than the 3PL project (`dani-mgs`). A cached git credential (Keychain or `gh` CLI) for the old account can cause pushes to fail with a 403 "Permission denied" even though the repo URL itself is correct. Fix: `git remote set-url origin https://<correct-username>@github.com/...` to force a fresh credential prompt, or clear the cached entry in Keychain Access / `gh auth login` as the correct account.
- `supabase link` fails on this machine with "does not have the necessary privileges to access this endpoint" — a known, currently-unresolved Supabase platform/CLI bug unrelated to actual account permissions. Workaround in use: `supabase db push --db-url '<pooler-connection-string>'` (Docker Desktop must be running; use the **pooler** connection string, not the direct `db.xxxxx.supabase.co` one — the direct one resolves to IPv6 and fails with `ECONNREFUSED` on networks without proper IPv6 routing).
- **Writing an RLS policy is not enough — Postgres checks table-level `GRANT`s before RLS is ever evaluated.** The initial schema migration created policies but never granted `authenticated` basic SELECT/INSERT/UPDATE/DELETE on the tables, so every write failed with `permission denied for table X` until a follow-up grants migration fixed it. Any new table needs both: RLS policies AND an explicit grant (or rely on the `ALTER DEFAULT PRIVILEGES` clause already in place, which should auto-cover genuinely new tables going forward).
- Supabase's dashboard **Triggers page filters by schema and can hide triggers on `auth.users`** under the wrong tab — a trigger existing and working correctly can look "missing" in the UI. Don't trust that page alone; confirm directly with `select * from pg_trigger where tgname = '...'` in the SQL Editor if a trigger's existence is ever in doubt.
- **Claude Code sessions don't have visibility into `supabase db push` commands you run manually outside its own tool calls.** A fresh session may flag caution about migrations "needing to be applied" even when they're already confirmed live — check this file's §4 (Current State) for what's actually confirmed before re-verifying from scratch, and keep §4 updated after every manual push so this doesn't compound.
- `supabase db reset` fails with a socket error if Docker Desktop isn't fully started yet — wait for the whale icon to settle.
- Migration files sometimes get created and applied but NOT committed to git — run `git status` after any Supabase CLI work and confirm the new `.sql` file is committed before moving on.
- `supabase login` sessions can expire/loop on a Keychain prompt — if a CLI command throws an auth error, just re-run `supabase login`.
- **Native browser/OS scrollbars are not a reliable way to signal "more content off-screen" and can render invisibly even when correctly styled.** After fixing the board's `min-w-0` clipping bug (gotcha above), a follow-up task asked to make the horizontal scrollbar on the board's column row persistently visible (not just on hover/active-scroll) via `::-webkit-scrollbar`/`scrollbar-color`/`scrollbar-width: thin` CSS. That CSS computed correctly (confirmed via `getComputedStyle`) but rendered zero pixels and reserved zero layout space in the Playwright MCP browser session used to verify it — `scrollbar-width: thin` and `::-webkit-scrollbar` alike, even with the "thin" keyword removed. This is a known class of problem: native scrollbar visibility depends on the OS's own "show scrollbars" setting (macOS in particular can force auto-hide-until-scroll regardless of page CSS) and on the specific browser/engine build's scrollbar theming assets, neither of which a page's CSS reliably controls end-to-end. **Fix used instead: don't fight native scrollbar theming — render your own indicator.** `board-client.tsx`'s `useHorizontalScrollThumb` hook tracks `scrollWidth`/`clientWidth`/`scrollLeft` (via a scroll listener + `ResizeObserver`) and drives a small absolutely-proportioned `<div>` track/thumb rendered below the row, hard-hidden by CSS (`scrollbar-width: none` + `::-webkit-scrollbar { display: none }`) from ever showing the native one underneath. This is guaranteed visible on load, in any browser, regardless of OS scrollbar prefs — and was the only approach that actually verified in a screenshot. **If a future task wants a visible scroll affordance anywhere else in this app, replicate this pattern (synthetic indicator + hidden native scrollbar) rather than trying `::-webkit-scrollbar`/`scrollbar-color` alone again** — budget time to discover this the same way if you skip straight to native-scrollbar CSS.
- **A `flex-1` element nested inside another flex container needs an explicit `min-w-0` (or `min-h-0` for columns) whenever a descendant relies on `overflow-x-auto`/`overflow-y-auto` to scroll instead of clip.** By default a flex item's `min-width`/`min-height` is `auto`, which means it won't shrink below its content's intrinsic size — so if that content is wider than the available space, the flex item itself grows to fit it instead of respecting the parent's bound, and the growth cascades up the ancestor chain instead of triggering the intended scrollbar on the nearer, correctly-configured `overflow-x-auto` container. This is exactly what took three attempts on the talent-acquisition board: `board-client.tsx`'s column row (`overflow-x-auto`) was correctly configured from the start, but `src/app/(shell)/layout.tsx`'s `<main className="flex-1 ...">` had no `min-w-0`, so at any viewport width where the columns' combined intrinsic width exceeded the available space, `main` (and the page around it) grew instead of letting the column row scroll internally — producing overflow/clipping that looked like "the scroll container is broken" when the actual bug was one ancestor level up. Fix applied: `min-w-0` added to that `main` element. **When a scrollable region clips instead of scrolling, check every `flex`/`flex-1` ancestor between it and the viewport for a missing `min-w-0`/`min-h-0` before touching the scrolling element's own CSS again.** This same pattern keeps showing up on ordinary `flex justify-between` header rows too (candidate name + status badge, board title + "Manage roles" link, History rows) — any two-sided flex row with variable-length text on one side needs `min-w-0` (or `flex-1 min-w-0`) on the growable side, or `flex-wrap`, or both, or narrow viewports clip it. Check for this by default on any new one, don't wait for it to be reported.
- **This UI kit (`@base-ui/react`, via shadcn's `sheet.tsx`/`dialog.tsx`) has no `asChild` prop** — that's a Radix convention this kit doesn't share. To render a custom trigger element (e.g. a styled `Button` as a `SheetTrigger`), pass it via the `render` prop instead: `<SheetTrigger render={<Button>…</Button>} />`, not `<SheetTrigger asChild><Button>…</Button></SheetTrigger>`. Passing `asChild` is a TypeScript error (`Property 'asChild' does not exist`), so this fails at typecheck, not silently at runtime — but worth knowing up front rather than rediscovering.
- **Supabase's default email sender has a very low rate limit meant for testing only.** It's fine for the occasional manual invite during development (and is the backstop confirmed working during the admin invite feature, step 2 — see §4), but real invite usage will hit `over_email_send_rate_limit` quickly. This needs a custom SMTP provider (e.g. Resend) connected in the Supabase dashboard before invites are used for real — not a code fix, nothing in this repo's Server Actions can raise Supabase's own project-level limit. Flagged during step 2, deferred until now as a reminder to actually do it before relying on invites at any real volume.
- **Base UI's `Sheet`/`Dialog` don't auto-close when a plain `<Link>` inside them navigates** — there's no implicit `SheetClose` wrapping every nav item the way some kits behave. If a Sheet holds navigation links (as `mobile-nav.tsx`'s slide-out menu does), it must be a controlled component (`<Sheet open={open} onOpenChange={setOpen}>`) that explicitly closes itself on route change, or the menu stays open over the new page after a tap. Do the state reset **during render**, not inside a `useEffect` — `useEffect(() => setOpen(false), [pathname])` triggers this repo's `react-hooks/set-state-in-effect` ESLint rule (an extra unnecessary render pass) and is flagged as an error, not a warning. The working pattern (see `mobile-nav.tsx`): track the last-seen `pathname` in state, and if the current `pathname` differs, call both setters directly in the render body (React's documented "adjusting state when a prop changes" pattern) — no effect needed.
- **Supabase's default email sender changed on June 3, 2026: any free-tier project created after that date cannot edit its Auth email templates at all** — the dashboard's Email Templates editor is locked to Supabase's own defaults (view-only) unless a custom SMTP provider is connected. Projects created before that date were grandfathered with template-editing still enabled; this project wasn't, since it was created after the cutoff. This is what actually blocked the hash-fragment-vs-`token_hash` template fix (below) from taking effect the first time it was tried — editing the template in the dashboard appeared to save, but had no effect on the emails actually sent, until Resend was connected as custom SMTP. **If a future Supabase-auth project's email templates seem impossible to change, or changes to them don't seem to take effect, check whether SMTP is connected before assuming the edit itself is wrong.**
- **The default invite/recovery email link uses a hash-fragment token (`#access_token=...`), which never reaches the server** — this is why the original invite flow silently landed on `/login` instead of `/set-password`, with no error anywhere to point at the real cause. The fix: customize the Invite/Reset Password email templates (once template editing is actually available — see the SMTP gotcha above) to use the `token_hash` query-param format pointing at `/auth/confirm`, which this app's route handler (`verifyOtp()`) can actually read server-side. **Worth checking for on any future project using Supabase auth links** — the failure mode looks exactly like a routing bug in application code, not a template/email-delivery misconfiguration, until you know this pattern exists.
- **A domain existing in Resend's dashboard does NOT mean it's verified** — check the actual DNS record verification status per-domain, not just presence in the domain list. "Not started" means the DNS records Resend generated were never actually added at the domain registrar; a domain in that state can't send mail through Resend regardless of how long it's been listed there.
- **`onboarding@resend.dev` is Resend's built-in test sender** — works immediately with zero domain verification, useful for unblocking real end-to-end testing of an email flow before a real domain's DNS records are set up and verified. Not meant for production sends to real users — see §7's open item on switching to a verified UpScaleSupport domain before this app's invite flow is used on a real hire.

Project-specific watch-item (not yet encountered here, but worth checking every session given the design history — see §10):
- Confirm the AI draft-generation call still only happens from a server action, never a client-side fetch. This app's design went through a version that called the Anthropic API directly from the browser before it was corrected — if any regression reintroduces that pattern, the API key would be exposed to anyone who opens dev tools.

- 2026-09-11 — App is named Client Fulfillment App, a sidebar shell of modules. Talent Acquisition Desk is the first module; Onboarding and Kickoff are planned but explicitly not built yet (disabled sidebar placeholders only).
- 2026-09-11 — Talent Acquisition routes and domain logic live under a `talent-acquisition/` folder specifically, so future modules don't get tangled into this one's tables or routes. `/settings` stays app-level.
- 2026-09-11 — Roles are a separate table from candidates (`role_id` FK), not a field on each candidate — avoids duplicating the same job description across every candidate on one requisition.
- 2026-09-11 — Talent Pool is a stage (`stage = 'talent_pool'`, nullable `role_id`), not a separate table — a candidate can move in and out of it via the same stage/role mechanisms used everywhere else.
- 2026-09-11 — AI drafting is single-shot generation per next-action, not a persisted chat thread — cheaper (stateless, no growing context to re-send), and simpler for a non-technical eventual hire to use than a chat interface.
- 2026-09-11 — Rejected calling the Anthropic API from the client directly (an earlier prototype iteration did this) — moved to a server-side action after recognizing it would expose the API key. See fragile-area note in §10.
- 2026-09-11 — Rejected LinkedIn/X scraping-based sourcing — LinkedIn's Talent Solutions API requires an enterprise partnership and Recruiter seat licensing; scraping-based workarounds (e.g. Proxycurl) carry real legal risk after LinkedIn's 2025 lawsuit against that category of tool.
- 2026-09-11 — Rejected embedding a Claude.ai Pro-subscription login inside the app to avoid API costs — Anthropic's terms don't allow routing a Free/Pro/Max login through a third-party application.
- 2026-09-11 — Adopted the UpScaleSupport Brand Guide v2 (locked 2026-07-23) as the app's design system, resolving the open CSS-framework question in favor of Tailwind CSS v4 + shadcn/ui, matching the 3PL project's pattern. The prototype's manila-folder visual styling is fully superseded — only its layout/interaction logic (columns, drawer, badges) carries forward; see `DESIGN_SYSTEM.md` section 6.
- 2026-09-14 — Any Server Action accepting a foreign-key ID into another org-scoped table (first case: `role_id` on candidates) re-verifies visibility via the caller's own scoped `SELECT`, rather than trusting the FK constraint alone. RLS on the referenced table (`roles`) only governs direct reads/writes of that table — it doesn't stop an out-of-org UUID from being accepted as a foreign key elsewhere, since FK constraints only check existence, not policy visibility. This pattern needs to be replicated for any future action taking an org-scoped foreign key. See fragile-area note in §10.
- 2026-09-14 — Added `vitest` as this repo's first test dependency, specifically because `BUILD_BRIEF.md` §6 and this task both explicitly asked for cadence logic tests — not a general decision to start testing everything. Chosen over Node's built-in test runner for being the more standard/ergonomic choice on a Next.js/TS project; no React rendering is under test here so no jsdom/plugin setup was needed, just `vitest run`.
- 2026-09-14 — `statusFor` checks `candidate.stage === 'talent_pool'` first and returns `'parked'` unconditionally, before ever looking at the computed next action — not derived from `nextActionFor`'s terminal flag. This matches the task's explicit requirement that Talent Pool always shows a neutral badge "rather than overdue," and keeps the no-pressure guarantee for parked candidates enforced in one obvious place instead of as an emergent property of `STAGE_CONFIG.talent_pool` having no touches/recurDays.
- 2026-09-14 — The board's drawer only exposes the stage selector and next-action badge, not notes/tags/role-reassignment (which the prototype's drawer does have). `BUILD_BRIEF.md` explicitly scopes those to Prompt 7's dedicated `/talent-acquisition/candidates/[id]` page — building them into the board drawer too would mean two places doing the same edit, one of which (the drawer) has less room and less context (no job-description panel, no script, no history) to do it well.
- 2026-09-14 — Used shadcn's `Sheet` component for the drawer rather than hand-rolling the prototype's fixed-position overlay + panel CSS — it's the standard composition for a slide-out detail panel and comes with focus management and animation for free.
- 2026-09-14 — Used shadcn's `Dialog` (not `Sheet`) for the new-candidate form — the prototype's own add-candidate modal is a centered box, not a side panel, and `Dialog` is the standard match for that shape versus the drawer's slide-in pattern.
- 2026-09-14 — The role picker in the new-candidate form is a single `Select` whose value is either an existing role's id, or one of two sentinel values (`"none"`, `"__new__"`) — not three separate controls (radio group + conditional select/input) — to keep it one mental model ("pick from this list, including two special entries") rather than a control that changes shape depending on another control's state. The three-way `role_mode`/`role_id`/`new_role_title` fields `createCandidate` actually expects are derived from that single piece of state via hidden inputs, keeping the Server Action's contract unchanged.
- 2026-09-14 — Changed the submit button's label from the prototype's literal "Add to Sourced" to "Add candidate" — the prototype always created candidates into `sourced`, but ours can also land in `talent_pool` depending on the role choice, so the old label would be actively wrong about half the time. Matching the prototype's *fields and flow* took priority over matching its exact copy where the two are now in tension.
- 2026-09-14 — The candidate detail page (Prompt 7) is the only place notes/tags/role-reassignment/job-description/script/history live — the board drawer stays permanently minimal (stage + next action), not just "for now." This is the split §7 flagged as open after Prompt 6; it's now settled rather than reconciled toward merging the two.
- 2026-09-14 — `scripts.ts`'s `scriptFor()` takes `companyName`/`recruiterName` as explicit function parameters rather than reading them from some shared settings module — keeps it a pure function like `cadence.ts`'s, and makes the caller (the candidate detail page) responsible for the one Supabase read each of those actually requires (`org_settings.company_name`, the caller's own `profiles.display_name`).
- 2026-09-19 — Introduced role-based authorization (`profiles.role`, `'admin' | 'member'`) as a second, orthogonal authorization axis alongside this app's existing org-membership-only model — **a genuine security-model shift**, not just a new column. Chosen over a separate `admin_users` table or a Supabase Auth custom-claim/JWT approach because it stays consistent with how this app already does everything else (a plain RLS-governed column on `profiles`, checked server-side via a helper, the same shape as `org_id`) — no new auth infrastructure, no JWT refresh-timing complexity. The tradeoff, deliberately accepted: `role` isn't in the JWT, so every admin check costs a fresh `profiles` SELECT (via `getUserRole()`) rather than being free to read off the token — acceptable at this app's scale, revisit only if admin checks become a hot path.
- 2026-09-19 — Enforced the new `profiles.role` column with a `before update` trigger (`prevent_self_role_escalation`), not by tightening the "profiles: update own row" RLS policy's `WITH CHECK` clause. RLS `WITH CHECK` clauses can reference a row's own new/old column values directly, but safely comparing against "the acting user's *own* role, read fresh, without recursively re-invoking RLS on `profiles` mid-check" is exactly the kind of self-referential-policy footgun `current_org_id()` (in the initial schema migration) was already written as a `security definer` function to avoid — a trigger sidesteps that class of subtlety entirely and is easier to reason about. See the fragile-area note in §10 before changing this.
- 2026-09-19 — `/admin`'s cross-user writes (role changes, display-name changes for someone *other* than the caller) go through `src/lib/supabase/admin-client.ts` (service-role, bypasses RLS) rather than adding a new RLS policy that would let an admin update any profile row. Considered an "admin bypass" RLS policy (`using (public.current_user_role() = 'admin')`-shaped) instead, but rejected it: it would mean *two* separate mechanisms end up enforcing admin authorization (a DB policy, and this app's own `requireAdminUser()` checks), which is more surface area to keep in sync, not less — and it would need the same kind of `security definer` self-reference care as `current_org_id()`/the escalation trigger already required. Using the admin client keeps authorization in exactly one place (the Server Action, in application code) and keeps "what bypasses RLS" to a single, obviously-named file, matching what the task that introduced it explicitly asked for.
- 2026-09-19 — `src/lib/supabase/admin-client.ts` is a rename of a previously-scaffolded `service.ts` (identical implementation — service-role client, `autoRefreshToken`/`persistSession` off) that existed since Prompt 1 but had zero callers until the admin page needed one. Renamed and reused rather than left in place with a second, parallel `admin-client.ts` created alongside it, so this codebase only ever has one RLS-bypassing client to reason about, not two with overlapping purposes.

## 10. DO NOT TOUCH / FRAGILE AREAS

- **The Anthropic API call must stay server-side.** An earlier prototype iteration called the API directly from the browser; this was corrected specifically because it would expose `ANTHROPIC_API_KEY` to anyone who opened dev tools. Now built for real as `generateSuggestedMessage()` in `src/lib/talent-acquisition/draft-actions.ts` — the only file in this codebase that calls `api.anthropic.com`, confirmed by direct inspection when it was built, not just assumed. `draft-generator.tsx` (the client component) only ever calls that `"use server"` action; it has no import of `config.anthropic` and issues no `fetch` of its own. Any future change here needs the same auth + org check described in `BUILD_BRIEF.md` §5 before it touches the API. Also worth knowing: **Anthropic's API rejects an unscoped (org-level) API key with a 400 unless every request also carries an `anthropic-workspace-id` header** — this app's own `ANTHROPIC_API_KEY` hit exactly this live, confirmed via a direct `curl`, not a code bug (see §6/§7). Optional support for the header exists (`ANTHROPIC_WORKSPACE_ID` in `config.ts`/`.env.example`) — set it only if the configured key is unscoped; a workspace-scoped key needs no such header at all.
- **`getUser()`, never `getSession()`**, anywhere auth state is checked server-side, per `SECURITY.md` — `getSession()` trusts a locally-stored JWT without revalidating it.
- **Every table gets `org_id` and RLS enabled on creation**, even though there's only one org today — this is what makes a future second org (or the eventual client/lead-gen app) a data change instead of a security rewrite. Don't add a table that skips this.
- **The Talent Pool stage (`talent_pool`) must not get a cadence config with `touches` or `recurDays`.** No reminder pressure on parked candidates is a deliberate design choice, not an oversight — adding one back would undo the reason the pool exists.
- **`roles.job_description` is the single source of truth for a requisition's JD**, not a per-candidate field — don't reintroduce a candidate-level job description column; it was deliberately removed to avoid duplicating the same text across every candidate on one role.
- **Any Server Action with a side effect (the AI draft generator, any future third-party API call) needs its own authorization check beyond RLS** — RLS protects direct DB reads/writes, but an action calling an external API needs an explicit org/ownership check per `SECURITY.md`.
- **Any Server Action accepting a foreign-key ID into another org-scoped table must re-verify visibility itself, not trust the FK constraint.** RLS on the referenced table only governs direct access to that table — a FK constraint just checks the row exists, not whether the caller is allowed to see it. `candidates-actions.ts`'s `assertRoleIsVisible` pattern (re-running the caller's own scoped SELECT on `role_id` before accepting it) is the template to copy for any future action taking an org-scoped foreign key.
- **`statusFor` must keep checking `talent_pool` before anything else, unconditionally.** It's not enough that `STAGE_CONFIG.talent_pool` has no touches/recurDays — a future change to that config (or a bug in `nextActionFor`) must not be able to make a parked candidate show as overdue. The explicit `if (candidate.stage === 'talent_pool') return 'parked'` at the top of `statusFor` is the actual guarantee, not an emergent property of the config.
- **Any future admin-only Server Action must call `requireAdmin()`/`getUserRole()` (`src/lib/auth/get-user-role.ts`) and check the result explicitly inside the action itself, not only hide the admin UI that links to it.** RLS's existing policies enforce org membership, not role — a signed-in member can already read/write everything a fellow org member can per current RLS, so nothing in the database itself stops a non-admin from invoking an "admin" action directly (e.g. via browser dev tools calling the action) unless the action's own code checks role. This is the same authorization-beyond-RLS pattern as the AI-draft-generator note above, extended from "is this the right org" to "is this the right org *and role*."
- **Don't simplify away or remove the `profiles_prevent_self_role_escalation` trigger** (added in `20260919090000_add_profiles_role.sql`) to "clean up" the schema — it's the only thing stopping an authenticated non-admin from `PATCH`-ing their own `profiles.role` to `'admin'` via a direct Supabase REST call, since the "profiles: update own row" RLS policy has no column-level restriction and can't express one. If this trigger is ever touched, preserve both properties: (1) a signed-in non-admin changing `role` gets a hard rejection, and (2) `auth.uid() is null` (a direct SQL Editor / service-role session, with no PostgREST-authenticated request) is still allowed through — that carve-out is what made the very first admin's manual SQL bootstrap possible before `/admin` existed, and is also *why* `/admin`'s own role-change writes (through the service-role `admin-client.ts`, where `auth.uid()` is likewise null) aren't blocked by this same trigger — both rely on the identical carve-out, so don't remove it thinking it was only ever needed once.
- **`src/lib/supabase/admin-client.ts` is the one place in this codebase that intentionally bypasses RLS — treat any change to it, or to what calls it, with the same scrutiny as an RLS policy change, not as routine refactoring.** It holds the service-role key, which has unrestricted read/write on every table and access to `supabase.auth.admin.*` (listUsers, inviteUserByEmail — capabilities that don't exist on the normal anon-key client at all). The client itself has zero authorization logic; every one of its current call sites (`/admin/page.tsx`, `src/lib/admin-actions.ts`) is only safe because each independently calls `requireAdminUser()`/`getUserRole()` first. **Never import this file into a Client Component** (it would fail at build time regardless, since `SUPABASE_SERVICE_ROLE_KEY` has no `NEXT_PUBLIC_` prefix — but don't rely on that failure as the actual safeguard; the convention of keeping it server-only is the intended one). If a future change adds a new call site, that call site needs its own `requireAdminUser()` (or equivalent) check — there is no shared middleware or wrapper enforcing this, it is purely a per-call-site discipline, the same as every other `requireUser()`/`requireAdmin()` check in this codebase. **Not every admin-only feature needs this client** — step 3 (candidate assignment) is entirely built on the normal RLS-scoped client, because RLS's own policies on `profiles`/`candidates` already happened to permit everything it needed; reach for `admin-client.ts` only when a normal, RLS-respecting query genuinely can't do the job (as with cross-user `profiles` writes in step 2), not by default just because a feature is "admin-only."
- **A `"use server"` file can only export async functions — a plain `const`/type export from one gets silently stripped from the client bundle, with no build-time error.** `candidates-actions.ts` originally exported `SOURCE_PLATFORMS` (a `const` array) alongside its Server Actions; it type-checked and built fine, and only failed at runtime the first time a client component that imported it actually rendered (`TypeError: SOURCE_PLATFORMS.map is not a function`), because Next.js's "use server" transform only preserves the async-function exports for the client reference and drops everything else without complaint. Fix: any plain data/constant a client component needs must live in its own ordinary module (see `source-platforms.ts`), never in the same file as the Server Actions that also use it — even though "just export it from the actions file" looks like the more natural, less-file-sprawl choice, it silently breaks the moment a client component (not just another server-side caller) imports it.
- **This UI kit's `Button` (`@base-ui/react`'s `Button` primitive) defaults `nativeButton` to `true`, and rendering it as a non-`<button>` element via the `render` prop (e.g. `render={<Link href="…">…</Link>}`, to get a styled, navigable "button") throws a console error at runtime unless `nativeButton={false}` is also passed — same `render`-prop pattern as `Sheet`/`Dialog`'s no-`asChild` gotcha already noted above, but this failure mode is different: it type-checks and builds fine, and only shows up as a runtime console error the first time the page actually renders, not as a build-time or lint error. `roles/page.tsx`'s Back-to-board button is the working example to copy: `<Button variant="outline" size="sm" nativeButton={false} render={<Link href="…">…</Link>} />`.
- **Unlike `Button`/`Sheet`/`Select`, this UI kit's `Card` (`src/components/ui/card.tsx`) is a plain `React.ComponentProps<"div">` wrapper with no Base UI primitive underneath and no `render` prop at all** — passing `render={<button/>}` to it (the pattern that works on `Button`) does nothing useful; it just spreads an unrecognized `render` attribute onto a `<div>`. When a `Card`-styled element needs to be a real interactive control (as the board's candidate cards did, to fix keyboard/screen-reader access), the working pattern is: keep `Card` as the non-interactive visual shell (border/radius/background), strip its own padding (`className="gap-0 p-0"` overrides its default `py-(--card-spacing)`), and nest a real `<button type="button" className="w-full ...">` inside carrying the actual padding, click handler, and `aria-label`. `candidate-card.tsx` is the working example to copy. **One follow-up trap this pattern walks straight into: `Card`'s base classes include `overflow-hidden`, and a `focus-visible:ring-*` class on the nested button — flush with the card's own edges — gets silently clipped by it.** A box's own shadow (which is what a Tailwind `ring` is) is only clipped by an *ancestor's* `overflow-hidden` when it extends past that ancestor's box; the button had nowhere to paint the ring without immediately hitting `Card`'s clip, so the button was genuinely focusable (Tab/Enter both worked, confirmed via the accessibility tree) with a ring class that computed correctly but rendered nothing. Fix: put the ring on `Card` itself via Tailwind's `:has()` variant (`has-[:focus-visible]:ring-3 has-[:focus-visible]:ring-ring/50`, plus `has-[:focus-visible]:border-work-blue` to match the existing hover treatment) rather than on the nested button — an element's own shadow is never clipped by its own `overflow`, only by an ancestor's. Also add `overflow-visible` on the `Card` instance as a second layer of insurance. Any future "real button inside a bordered `Card`" fix needs to check for this the same way — a ring class present in the DOM is not proof it's visible; screenshot the actual focus state, don't just confirm the accessibility tree shows focus.
- **Supabase auth email links (invite, recovery, magic link) default to a hash-fragment session (`#access_token=...`), which a server-side route handler can never see — this is a real gotcha worth checking for on any future project using Supabase auth links, not specific to this app.** This was the actual root cause of the invite flow doing nothing when first built: the fragment never leaves the browser, so no route handler code, however correctly written, can read it. The fix has two parts, and both must be true together or the flow silently fails again:
  1. **Code side (in this repo, done)**: `/auth/confirm/route.ts` reads `token_hash`/`type` from the query string and calls `verifyOtp()` — Supabase's documented server-side-verification pattern, which requires the *query-param* link format, not the hash-fragment one.
  2. **Dashboard side (outside this repo, done — 2026-09-21, by the user directly)**: the Supabase project's **Invite user** and **Reset Password** email templates (Authentication → Email Templates) had to be changed from Supabase's default confirmation link to `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=invite&next=/set-password` (and the `recovery` type equivalent for Reset Password). **Nothing in this repo can see, set, or verify this setting — Claude Code has no access to the Supabase dashboard.** If a future invite or password reset silently fails to reach `/set-password` (lands on a generic Supabase page, 404s, or the link just "does nothing"), check these templates first, before assuming the route handler code is broken — it's the same class of failure that looks exactly like a code bug from the receiving end.
  - Also depends on `NEXT_PUBLIC_SITE_URL` being set to the real deployed origin in every environment (Vercel env vars included) — if it's left unset or wrong, both `inviteUser` and `resetUserPassword`'s `redirectTo` will point at the wrong host regardless of the template being correct.
- **`admin.auth.admin.deleteUser()` requires the FK-behavior migration (`20260921090000_fix_fk_behavior_for_user_deletion.sql`) to be applied before it will succeed for any user who has ever created a role, candidate, candidate_history entry, or candidate_draft.** Without it, `profiles.id`'s FK to `auth.users(id)` and the four `created_by`/`generated_by` FKs to `profiles(id)` all default to blocking (`NO ACTION`) — `deleteUser` (`admin-actions.ts`) catches the resulting `23503` and reports a specific "migration hasn't been applied yet" message rather than a generic failure, but the delete still won't succeed until the migration actually runs. This migration has not been applied to the live database as of this writing — see §6. Once applied, `candidates.assigned_to`'s FK deliberately stays blocking (unlike the four attribution columns, which become `set null`) — don't "fix" that one the same way; `deleteUser`'s own explicit pre-check is the intended guard there, not the database.
- **`candidates` has two foreign keys to `profiles`** (`created_by`, `assigned_to`) — any future PostgREST embed of `profiles` off of `candidates` should disambiguate which one via the column-name hint (`profiles!assigned_to(...)` or `profiles!created_by(...)`), not a bare `profiles(...)`, which PostgREST may reject as ambiguous with two FKs present. Verified the `!assigned_to` form works correctly (both null and populated) directly against the live REST API before using it — didn't independently confirm the bare form actually errors, so treat "disambiguate" as the safe default here rather than a proven-necessary one. `candidates/[id]/page.tsx`'s `assignee:profiles!assigned_to(id, display_name)` is the working example to copy.
